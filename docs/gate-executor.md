# Gate executor

`packages/gate/src/internal/executor.ts` is an internal write execution API. It registers trusted adapters at gate startup, loads the stored schema-validated intent, checks its canonical hash and approval reference, resolves its unique enabled pinned connector operation, and passes one immutable request to an injected gate-owned transport. There is no HTTP write proxy or browser endpoint here. The read proxy in #14 continues to refuse writes. Browser access through Tailscale Serve is tracked separately in #178 and #85.

## Request binding

`payload_hash` signs the canonical **whole intent**, such as `{"args":{"add":["work"],"messageIds":["msg-1"]},"kind":"email.label"}`. A provider body such as `{"provider_arguments":{"add":["work"],"messageIds":["msg-1"]}}` has a different shape and therefore a different hash. Comparing those two hashes would refuse every legitimate provider adapter.

A trusted `UpstreamWriter` implements `buildRequest(intent)` and `intentFromRequest(request)`. The executor copies method, URL and canonical body bytes into a frozen snapshot, reconstructs an intent from those exact values, schema-validates it, and compares its canonical hash to the approved intent hash. The decoder must validate all method, URL and provider arguments that affect intent semantics. A wrong body, target route or verb therefore fails before transport. Both adapter methods belong to the trusted gate registration boundary; a malicious adapter implementing both dishonestly is outside this check's protection. Connector/model output cannot register writers.

`WriteTransport` receives the trusted connector, operation and intent kind alongside exact request bytes and an idempotency key. The gate-owned transport must enforce the pinned write route and host allowlist, inject credentials from the vault, disable redirects, bound upstream work, sanitize results and handle revoked grants. Tokens and caller-controlled headers are absent from the writer contract. Actual provider adapters and credential-backed write transports are part of connector issues #20–#23; this module accepts their internal port without exposing a generic external-write endpoint. A uniquely pinned enabled write operation and a non-open connector are required immediately before dispatch, including undo.

## Durable outcomes and undo

`execution_attempts` permanently claims `(intent_id, direction)` before the asynchronous call. Concurrent callers, independent database handles and restarted processes cannot initiate a second attempt. Completed calls replay the audit-bound recorded result. A claim with no completed result returns `outcome_unresolved`: the upstream may already have accepted the call. The executor never releases the claim or retries an uncertain outcome. This is an at-most-one-attempt guarantee, not an atomic transaction between SQLite and an external service. An operator must reconcile uncertain upstream outcomes before a new intent is proposed. The execute key is the intent id; undo uses `<intent id>:undo`. A provider transport sends that key using the provider's supported idempotency mechanism.

After success, one SQLite transaction records the upstream reference, result, inverse and append-only audit reference and moves the intent to `executed`. Approval-tier execution requires a consumed approved decision matching the intent hash and an unrevoked enrolled credential; it records no automatic inverse. Automatic actions can record a schema-valid inverse. The inverse and result are hashed together in the immutable execution audit entry and checked before replay or undo. Undo only permits original automatic actions and refuses send, forward, reply, trash and delete inverses. It uses the same request binding, claim and call path, preserves `executed`, and adds an `undone` history entry. Successful undo has its own recorded result so it also replays without a second call. Failures and refusals record reason codes and hashes, never payloads or upstream error text.
